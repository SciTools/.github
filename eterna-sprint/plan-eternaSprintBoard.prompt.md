# Plan: Eterna-Sprint Board automation (new GitHub Project)

## Context (SciTools/.github repo, workspace folder "dotgithub")
- Repo is the special org repo `SciTools/.github`. Existing `peloton/` folder automates
  a GitHub Projects v2 board ("Peloton") for community triage. Workflow:
  `.github/workflows/peloton.yml` (cron daily + workflow_dispatch w/ update_loop_minutes,
  uses tibdex/github-app-token w/ secrets.AUTH_APP_ID/AUTH_APP_PRIVATE_KEY, conda installs
  peloton/requirements.txt, runs `peloton/update_project.py`).
- peloton/update_project.py uses sgqlc against GitHub GraphQL. Key pieces:
  PaginatedQuery/PaginatedMutation base classes, ProjectItemsQuery, ProjectFieldsQuery,
  IssuesQuery/DiscussionsQuery (search type=ISSUE covers Issues+PRs), PelotonTeamQuery,
  AddIssuesMutation, AddDraftsMutation, ClearPelotonDateMutation, RemoveItemsMutation,
  UpdateItemsMutation. Peloton needs heavy custom-field machinery because: (a) it tracks
  Discussions as "draft" items with no native content link (needs custom `_linked_id` text
  field), (b) it classifies author/commenter membership (team vs external vs bot), (c) it
  auto-sets many fields incl. a "next peloton date" snooze field.
- github_schema.py is autogenerated via update-schema.sh (sgqlc-codegen from GitHub's
  GraphQL schema) - large, not hand-edited/vetted.
- Project Views/fields are configured manually in the GitHub UI (GraphQL API has no way to
  create/configure Views); peloton/project_settings.md is a manual backup doc of that config.
- An empty `eterna-sprint/` folder already exists at the repo root (user-created) - this is
  the target folder name for the new board's automation (confirmed by user: folder name is
  "eterna-sprint", not generic "sprint").

## User requirements (from clarifying Qs)
- Repo/org scope: SAME as Peloton's GITHUB_QUERY_CONDITIONS (org:SciTools
  org:SciTools-incubator org:SciTools-classroom, -repo:SciTools/cartopy,
  +bjlittle/geovista +pp-mo/ncdata +pp-mo/ugrid-checks).
- Track Issues + PRs only, NOT Discussions.
- Board style: "sprinting board" - ONE List view sliced by Repository (not separate views
  per repo), plus one final cross-repo KANBAN view of "active" items only.
- "Active" = a manually-assigned Status value (team drags cards); NOT automated by script.
  Only the final cross-repo view is Kanban (grouped by Status); the repo-sliced view is a
  plain List.
- Script must NEVER write/automate the Status field - purely manual, like a real sprint board.
- Code org: new STANDALONE folder `eterna-sprint/`, NOT a shared library with peloton/ -
  mirror Peloton's folder structure (own github_schema.py, update-schema.sh, requirements.txt).
- GitHub Project not yet created - user will create it manually before implementation and
  hand over the project node ID (and any field IDs if needed).
- Refresh cadence: same as Peloton (daily cron + workflow_dispatch w/ update_loop_minutes).
- Additional cross-repo-only (not per-repo) List view: "Assigned or review requested".

## Key design simplification identified
Because Status is manual and Discussions are excluded, the new script needs NO custom
project fields at all:
- Items are always linked Issues/PRs (never drafts) -> can read the native
  `content { ... on Issue { id } ... on PullRequest { id } }` link directly, no need for
  Peloton's custom `_linked_id` text field / use_draft logic.
- No field-value pushing needed -> no ProjectFieldsQuery/UpdateItemsMutation/
  ClearPelotonDateMutation/AddDraftsMutation/PelotonTeamQuery/SelectionIds equivalent needed.
- Script reduces to: query matching issues/PRs (same scope+threshold pattern as Peloton) +
  query current project items -> add newly-matching items (AddIssuesMutation-style) ->
  remove orphaned/stale items (RemoveItemsMutation-style). No metadata field sync at all.
- The repo-sliced List view assumes GitHub's native per-item Repository meta-field
  (auto-populated for multi-repo projects) supports "Slice by" - NOT verified, flagged as
  a risk/assumption to check once project is created.

## Plan structure (as presented to user)
Phase 0 (manual, user, parallel): create GitHub Project v2 ("Eterna Sprint") in SciTools
  org (default template w/ built-in Status field, add any extra status options wanted
  e.g. In Review/Blocked), configure one List view sliced by Repository + final cross-repo
  Kanban "Active" view (group by Status, filtered to active status value(s)) + one more
  cross-repo List view "Assigned or review requested" (single view spanning all repos, not
  duplicated per-repo - confirmed via follow-up question), hand back project node ID.
  - "Assigned or review requested" view: assignee filter = `-no:assignee` (same pattern
    Peloton uses for its "Progress report" view); review-requested filter for PRs likely
    `-no:reviewers` or similar native qualifier (not yet confirmed against the live GitHub
    Projects filter UI at setup time).
  - RISK: GitHub Projects view filters are traditionally AND-only (space-separated
    qualifiers), same as GitHub search syntax. A true OR between "has assignee" and
    "has review requested" may not be expressible as a single filter string. Flagged to
    user to verify in the UI when building this view - if OR isn't supported, options are:
    (a) check whether GitHub has since added comma/OR syntax across qualifiers, (b) split
    into two separate views side by side, or (c) pick whichever single condition matters
    most. No code changes needed either way - this is pure manual View configuration.

Phase 1 (parallel w/ Phase 0): scaffold `eterna-sprint/` folder (already exists, empty) -
  requirements.txt, update-schema.sh, github_schema.py (generated/copied), README.md,
  project_settings.md (modeled 1:1 on peloton/ equivalents).

Phase 2 (depends on Phase 1 + project ID from Phase 0): implement
  `eterna-sprint/update_project.py` - adapt PaginatedQuery/PaginatedMutation/run_operation/
  ENDPOINT pattern verbatim; simplified ProjectItemsQuery (native content id); trimmed
  IssuesQuery (id, url, number, title, created_at, updated_at, closed_at only - no
  author/commenter classification, no votes/labels/discussion_wanted, no final-comment
  logic); AddIssuesMutation + RemoveItemsMutation (copy pattern); main() keeps
  --bearer_token/--update_loop_minutes/--verbose CLI + logging-to-file convention
  (latest_eterna_sprint_update.log), loop does fetch -> add -> remove only (no
  field-update step). Drop entirely: DiscussionsQuery, PelotonTeamQuery, ProjectFieldsQuery,
  UpdateItemsMutation, ClearPelotonDateMutation, AddDraftsMutation, SelectionIds.

Phase 3 (depends on Phase 2): `.github/workflows/eterna-sprint.yml` modeled on
  `.github/workflows/peloton.yml` (same cron/dispatch shape, reuse AUTH_APP_ID/
  AUTH_APP_PRIVATE_KEY secrets, conda install eterna-sprint/requirements.txt, run
  eterna-sprint/update_project.py).

Phase 4 (depends on 1-3): update root README.md "Contents" list with an `eterna-sprint/`
  bullet (same style as existing Peloton bullet).
